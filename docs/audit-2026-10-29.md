# ShelfLedger project audit — 29.10.2026

The largest release risks are incomplete loan transactions and location cycles accepted by snapshot import. The largest measured performance problem is row-by-row import staging: importing five rows into a roughly 5,000-work library took **75 seconds** in the local debug build. The sell queue took **5.24 seconds** at that size.

This audit also implements the requested ISBN fallback, defers the barcode decoder, and fixes indexed cover retrieval. The other findings below remain open. This is a source, test, browser, and local runtime audit; it is not a certification of every platform, dependency, or possible input.

## Changes completed in this audit

### Automatic third-source ISBN lookup

The automatic chain is now local cache → Open Library → Google Books → ISBN Search. It advances after a miss, quota error or network failure, and stops after a match. The third source parses only the public book-information block and requires the requested checksum-valid ISBN-13 or its ISBN-10 equivalent. Related books, snippets, advertisements and prices are not imported. Missing page counts/languages remain absent.

The user's example, `9786067882629`, returned Open Library 404 and Google Books 429 in live checks. [ISBN Search](https://isbnsearch.org/isbn/9786067882629) returned an exact edition record, with Neil Gaiman as author. Its title is spelled `Mitologie Nordiča`; the app preserves the provider's wording and asks the user to review it. The [publisher's edition page](https://www.editura-art.ro/info/carte/mitologie-nordica) spells it `Mitologie nordică` and lists 256 pages/January 2018, while ISBN Search lists 2017 and no page count. Finding an exact ISBN is not a guarantee that every metadata field is correct.

Optional Open Library author enrichment stops before the provider deadline and retains completed names, so an already-matched edition can still be returned. Each automatic provider operation is bounded to 12 seconds; individual requests retain the existing 10-second timeout and 2 MiB response limit. Only `isbnsearch.org` was added to the HTTPS host allowlist. Cross-host redirects remain blocked. A changed page or challenge is reported as provider unavailability, not bypassed or represented as a definitive miss. Any earlier provider failure is retained when no source succeeds.

Successful results retain their source and are cached for offline use, including ISBN-10/13 equivalence. Android retains its no-INTERNET policy. UI text/source attribution and all eleven language bundles were updated, as were the privacy and metadata docs. No schema or IPC contract change was needed.

No provider covers every issued ISBN. Manual entry and explicit Libris URL import remain necessary escape routes. The new HTML source is less stable than a versioned API; a future metadata diagnostics view should expose provider failures without overwhelming the add-book flow.

### Decoder loaded only when needed

`src/lib/barcode.ts` now dynamically imports the locally bundled ZXing decoder only when a usable frame needs the JavaScript fallback. Library browsing, ISBN validation and successful native barcode detection do not load it. This preserves offline native-app scanning and existing camera lifecycle handling. Regression tests cover native detection without importing ZXing, fallback decoding, and unreadable frames.

The LibraryView chunk fell from 416,648 to **27,264 bytes** (93.5% smaller). The decoder is now a separate 416,490-byte chunk. Total JavaScript increased from 1,325,051 to 1,353,133 bytes; this is an initial-loading improvement, not an overall download-size reduction.

### Cover retrieval uses the primary key

`src-tauri/src/repositories/covers.rs` now validates the `covers/<UUID>.jpg` logical path and queries `WHERE id = ?`. The old concatenated predicate made SQLite scan the entire cover table. `EXPLAIN QUERY PLAN` changed from `SCAN edition_covers` to `SEARCH ... USING INDEX sqlite_autoindex_edition_covers_1 (id=?)`. Existing save/replace/remove tests and additional invalid-path cases protect the behavior. Cover display already used an IntersectionObserver and a local cache; those were retained.

## Open findings, ordered by impact

P1 means address before describing the release as robust for ordinary library use. P2 means a material correctness, usability or scaling improvement. Evidence is marked **reproduced** or **source review**.

### 1. P1 — Loan operations can leave partial state

**Reproduced.** `src-tauri/src/domain/loans.rs:238` inserts a loan, changes the copy state, and records an event as separate writes. With a temporary trigger rejecting the copy update, lending returned HTTP 500 but left **one active loan on a copy still marked owned**. Returning a copy has the same multi-write structure.

Use a single transaction for eligibility checks, loan insertion/return, conditional copy transition and activity event. Preserve the partial unique index as a concurrency backstop. Acceptance: injected failure at each write rolls back everything; concurrent lend/dispose actions cannot create contradictory ownership and loan records.

### 2. P1 — Snapshot import permits cyclic locations

**Reproduced acceptance; downstream loop established by source review.** A format-4 snapshot containing a location whose parent was itself imported successfully. Foreign keys permit this relationship. `src/features/settings/SettingsView.tsx:151` follows parent links without a visited set, so such imported data can make Settings render loop indefinitely. The UI was not deliberately frozen during this audit.

Validate the complete merged hierarchy before commit, including cycles involving existing and imported locations. Add a defensive visited set in label rendering. Acceptance: self-cycles and two-/multi-node cycles reject atomically; valid nesting and missing-parent handling remain covered.

### 3. P1 — Import cost grows with the whole library for every row

**Measured and source-confirmed.** `src-tauri/src/domain/import.rs:757` and `:783` call `snapshot::stage_local` per incoming item. Staging exports all tables, creates a migrated database and reinserts the snapshot; merging exports again and rebuilds FTS. Large base64 cover data amplifies the copying.

Refactor toward one staging session per import or transaction/savepoint-based repository writes per row, with incremental FTS updates. Preserve preview decisions, duplicate handling, per-row rollback, full snapshot validation and import-job history. Do not remove those protections to improve speed. Acceptance: importing a fixed five-row batch no longer clones/reindexes the whole database five times; regression fixtures include covers, duplicates and a failing middle row.

### 4. P1/P2 — Safety backups exist but cannot be recovered through the app

**Reproduced.** Restore writes a `shelfledger.pre-restore-<UUID>.zip` beside the live database (`domain/backup.rs:263`). The download/export allowlists accept only managed `backups`/`exports` locations. After a successful restore, the safety archive existed but downloading the path shown in the success message returned 404. Settings does not provide a safety-backup history/recovery flow.

Store safety archives in the managed backups directory and expose typed list/download/restore actions. Keep path allowlists strict. Acceptance: restore → download previous library → restore previous library works through the UI on web and native, including profile switching.

### 5. P2 — Search materializes the library and silently caps results

**Measured and reproduced.** `repositories/works.rs:254` calls `list_work_summaries` for the entire library and filters it afterward. A one-match search therefore scales with unrelated books. The FTS query limits matches to 200; 201 deliberately matching works returned 200, with no next-page/total indication. Frontend sort/filter applies after this truncation.

Fetch summaries only for matched IDs and add a typed paged search with deterministic sorting, filters applied before pagination, and `hasMore`/total metadata. Acceptance: all 201 matches are reachable; page ordering is stable; one-match SQL does not read all work summaries. Large-list virtualization remains a separate roadmap decision.

### 6. P2 — Sell queue and reading use repeated per-item queries

**Measured and source-confirmed.** `domain/finance.rs:422` fetches acquisitions, valuations and listings for each candidate copy, then selects relevant entries in memory. `domain/reading.rs:73` fetches progress history separately for each session. The reading UI also requests the full unfiltered session list and performs per-row searches; React Query deduplicates that request, so this is not one frontend HTTP request per card.

Use joins/aggregates or batched queries for the required latest values, return summary DTOs, and load full histories only when opened. Pass the existing session into cards. Preserve per-currency calculations and historical valuation evidence. Acceptance: query count is bounded by page size/batches rather than three queries per copy, with the same ranking and financial results.

### 7. P2 — Exact-title search fails on punctuation

**Reproduced.** Creating `L'Étranger` and `Audit alpha/beta`, then searching for the full title, returned zero matches. Searching `Étranger` or `beta` found the books. Query cleanup removes punctuation in ways that disagree with the FTS tokenizer.

Split user terms consistently with the tokenizer, preserving Unicode and the separate ISBN normalization path. Test apostrophes, slashes, hyphens, diacritics and multiword prefix matching. Avoid exposing raw FTS syntax to user input.

### 8. P2 — Dashboard shows maximum page as latest page

**Reproduced.** Logging page 200, then correcting progress to page 150 on a later date, left dashboard `latestPage` at 200. `domain/dashboard.rs:38` uses `MAX(p.page)`.

Select the latest event by event date with a deterministic tie-breaker and a defined policy for percentage-only entries. Acceptance: later corrections can reduce displayed progress, without changing historical events.

### 9. P2 — A loan can be returned before it was lent

**Reproduced.** A loan dated 28.10.2026 accepted a return dated 01.10.2026. Compare normalized/defaulted dates inside the loan transaction. Test omitted dates, same-day timestamps and future lending dates so validation agrees with storage conventions.

### 10. P2 — Backup/export limits are inconsistent

**Source review; oversized artifacts were not generated.** Web uploads cap request bodies at 64 MiB, native staging allows 512 MiB, and restore caps an extracted database entry at 512 MiB. Backup creation has no matching preflight. Cover data can make a valid export too large for its destination restore path; compressed ZIP size and uncompressed database size are different limits.

Define explicit archive, entry and transport limits, show a preflight error before producing unusable exports, and consider streaming for large libraries. Test boundary cases, compressed large entries and a realistic cover-heavy library.

### 11. P2 — Library navigation discards context; errors can look empty

**Navigation reproduced; error handling from source review.** Searching `specimen`, opening a result and returning to My Library cleared the search and showed the full list. Filters, sort, display mode and scroll are component state/reset on navigation. Reading/Loans views can show an empty state after a query error; some return mutations have no visible error feedback.

Preserve library state per profile, restore scroll on back navigation, distinguish empty/error/loading states, and add a recoverable application error boundary. Acceptance: the back path restores the same results and position; failed reads offer retry; failed returns remain visible and actionable.

### 12. P2 — Additional loading and web-server inefficiencies

**Build measurement and source review.** Eleven dictionaries plus locale support JSON total approximately 414,886 source bytes and are statically imported. The decorative library image is 2,120,877 bytes. Bundled font files total 3,270,588 bytes on disk, but unicode-range loading means this is not the English-page transfer size. The main JavaScript chunk still exceeds Vite's 500 kB warning threshold.

Consider loading only the active local dictionary, optimizing the decorative image, and profiling actual font transfers. The web middleware applies `no-store` to hashed static assets as well as private API responses; static serving synchronously reads files on each request. Allow immutable caching/compression for fingerprinted public assets, while preserving no-store for private API/download responses. Measure startup with a cold browser cache before choosing further changes.

### 13. P2 — Open browser can retain an expired process token

**Source review, not restart-reproduced.** `src/lib/api.ts:75` caches the successful session-token promise. The server token changes on process restart, but a 403 does not refresh the cached promise. A tab can require reload after restart. Add one bounded token refresh/retry with explicit handling that cannot blindly repeat an operation whose completion is unknown. Keep origin/host and session protection intact.

## Performance baseline

Rust **debug** build, same machine, local HTTP transport, synthetic library with one edition, owned copy, finished reading session and progress event per seeded work, without covers. Read figures are medians of three calls; each import figure is one five-row batch. One pre-existing fixture and earlier import batches explain actual work counts of 101, 1,006 and 5,011. These are diagnostic measurements, not release-build latency promises or measured gains from the new changes.

| Seeded works | One-match search | List all works | Sell queue | Reading sessions | Import five rows |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 2.20 ms | 3.41 ms | 22.44 ms | 10.62 ms | 770.43 ms |
| 1,000 | 17.00 ms | 24.13 ms | 396.37 ms | 100.61 ms | 8,787.55 ms |
| 5,000 | 69.66 ms | 117.93 ms | 5,240.86 ms | 521.50 ms | 75,003.21 ms |

Before this audit's changes, the production main chunk was 704,993 bytes (211,511 gzip); the LibraryView chunk was 416,648 bytes (110,461 gzip). All JavaScript totaled 1,325,051 bytes. Moving code to a deferred chunk reduces initial loading rather than eliminating the decoder from the application. The new main chunk is 705,969 bytes (212,046 gzip), LibraryView is 27,264 (8,923 gzip), and the deferred decoder is 416,490 (109,474 gzip). See [build evidence](audits/2026-10-29/bundles-after.json).

## Architecture, safety and release observations

The work/edition/copy model, separate reading/ownership states, integer money and per-currency reporting are sound foundations. Existing tests cover foreign keys, money, duplicates, snapshots, covers and request/path guards. Typed IPC, bound SQL parameters, narrow provider hosts, body limits, local-only web serving and disabled Android networking provide useful boundaries. No new remote messaging, telemetry, permissions or fabricated valuations were introduced.

Domain modules contain substantial SQL despite the repository-layer convention. Move touched queries into repositories while fixing the hotspots; a broad rewrite would add risk without proving a benefit. Keep Rust/TypeScript DTO synchronization explicit. Add focused fault-injection and import/query-count regressions to CI; browser workflow coverage is currently mostly manual. The `pnpm lint` script actually performs type checking and a production build, not a standalone lint rule pass.

The JavaScript dependency audit reported zero advisories at audit time. A current local Rust advisory scan was **not** performed because `cargo-audit` was not installed; an existing CI workflow is not evidence that it ran here. Windows/Linux builds, signed installers, Android physical-device behavior, real camera capture, broad screen-reader testing and full release-mode performance profiling remain unverified in this audit.
